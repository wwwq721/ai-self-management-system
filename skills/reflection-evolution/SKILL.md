# 反思进化

## 引用文件

- 用户级 `MEMORY.md`（本机文件，**未随公开仓上传**；格式见 [examples/MEMORY.example.md](../../examples/MEMORY.example.md)）：阅读或更新，用于反复出现的错误模式与少见错误（教训暂存；沉淀为规则时迁出到对应治理文件）。
- [../../OPERATIONS.md](../../OPERATIONS.md)：提示：创建或修改任何 skill、记忆或治理文件之前先阅读 [../../OPERATIONS.md]（本处为提示、不构成依赖引用）。

使用本 skill 将错误转化为未来的行为约束。不要把反思仅仅写成道歉文字。

## 工作流

0. **在撰写独立经验前，先匹配现有 skill**
   - 在把任何内容写入 MEMORY.md 或创建新 skill 之前，先搜索当前平台可用的 skill 目录，查看是否有某个 skill 的职责覆盖了这条经验。
   - 问自己："这条经验是在扩展/改进某个现有 skill 的工作流、决策规则或最佳实践吗？"
   - 如果是 → 把经验吸收进该 skill（见第 8 步）。先加载 `skill-creator`，再修改目标 skill。
   - 如果没有现有 skill 覆盖 → 进入第 1-6 步，然后在第 8 步决定是否需要创建新 skill。
   - 这一步在任何记忆写入或文件编辑之前执行。不要先写再事后合并。
   - **自我参照**：当经验本身是关于反思过程或 skill 创建过程时，`reflection-evolution` 和 `skill-creator` 本身就是匹配目标。先检查这条经验是否属于本 skill。

1. **区分事实、推断与授权**
   - 事实：实际说过、读过或验证过的内容。
   - 推断：我所假设的内容。
   - 授权：用户明确确认过的内容。
   - 如果某个编辑/动作是基于推断而非授权做出的，就把这指认为失败所在。

2. **找出共性病灶，而非表面症状**
   - 拒绝浅层修复，例如当真实模式更宽泛时，只写"记得检查 X"。
   - 问自己："哪些先前的错误共享这一结构？"
   - 当前记忆中的典型根因模式：我的默认做法/推断/提案绕过了用户确认或可适用的 skill/规则。

2a. **重复错误：深挖根因，而非仅仅引用 T 编号**
   - 在结束一次反思前，检查当前错误是否映射到某条已有的 T 记录。
   - 如果是：说明先前的经验未能阻止这次复发。不要只引用 T 编号就停下。
   - 带着"为什么上次的修复没能阻止这次发生？"这个问题回到第 1 步。
   - 产出一条新的反思，扩展或取代更早的那条记录，并给出更深的根因。

3. **制定修复方案**
   - 在第 2 步根因分析完成后、任何编辑或 T 记录写入之前，先制定修复方案。
   - 把根因追溯到源头：错误是否可追溯到某条不完整、含糊或缺失的规则/指令？如果是，**按 `OPERATIONS.md`「规则先行原则」第 3 步定位管辖文件**——"源文件"指根因所在的**管辖**文件，不是话题最近的那个。
   - 列出每项计划中的改动：哪个文件、改什么、为什么。
   - 决定修复方向时可参考下方的未修复层级参考表（非强制），但真正的约束是清单本身。
   - 动手之前，过一遍这三条修改约束：
     (a) 本次改动是否违反目标文件已有的规则？
     (b) 新内容是否与同一文件内的已有内容矛盾？
     (c) 是否留下了盲点——写的规则自己适用不了？
   - 对于治理文件：先展示方案并等待用户同意，再做编辑——**判据与范围见 `OPERATIONS.md`「治理文件修改流程」**，不在此列子集。
   - 对于非治理文件：列出后即可执行（按 OPERATIONS.md 中"改动前告知"的要求）。
   - "只分析、无方案"不是反思的有效终点。

   ### 未修复层级参考（非强制）

   决定在哪里应用修复时，可参考以下映射：

   | 失败类型 | 根因 | 典型修复目标 |
   |---|---|---|
   | 不知道约定/规则 | 知识缺口 | L1 — 新建或更新 Skill |
   | 知道但不遵守 | 指令缺口/冲突 | L2 — 修改治理文件 |
   | 产出坏结果但通过审查 | 执行缺口 | L3 — 加 Hook 或强制检查步骤 |
   | 范围漂移（多做了/少做了） | Agent 定义 | L4 — 缩小或拆分 Agent |
   | 会话间产出不一致 | 指令不一致 | L5 — 审计冲突指令 |

   **修复手段优先级：直接修源文件 > 写入记忆 > 创建新 skill。** 如果根因是某文件里有错误的指令或规则，直接改那个文件——不要绕过它去记忆里加补丁或新建 skill 兜底。记忆和 skill 是源文件修不了时的替代路径，不是首选。

4. **让规则约束我的下一个动作**
   - 反思期间写下的任何规则都必须立即约束我接下来的行为。
   - 在放置或编辑一条规则前，先确认它约束的是谁、哪个文件/skill 拥有权威，以及引用的方向是否合法。

5. **把反思转化为可执行的触发器**
   按如下结构编写或更新记录：
   - `错误`：具体事件。
   - `浅层解释`：诱人但不足够的解释。
   - `深层病灶`：跨案例可复用的模式。
   - `下次动作`：下次的第一步具体动作。
   - `预警信号`（可选）：当观察到什么时，这个错误可能正在发生。

6. **只持久化会改变行为的内容**
   - 用户级别的教训与少见错误写入用户级 MEMORY.md（暂存）；沉淀为行为规则时，按 OPERATIONS「治理文件修改流程」第 7 步的归类标准迁到对应治理文件。
   - 项目特有的经验写入工作区每日日志或项目记忆。
   - 不要粘贴长篇的道歉叙述；保持记录可检索、以行动为导向。

7. **当出现重复或冗余模式时，整合记忆**
   - 反思常常在记忆文件中浮现出重复内容：同一规则被多次复述、同一经验出现在多个每日日志中、已被制度化的模式仍以原始记录形式存储。
   - 发生这种情况时，按相同的"扫描 → 分析 → 合并 → 精简"模式执行一次记忆清理：

   **扫描**：列出每日日志，阅读用户级 MEMORY.md 与当前项目的 `memory/` 目录。
   **分析**：识别重复项（同一事实/规则出现在多天）、制度化内容（已有治理规则覆盖的经验）、以及一次性记录（工具错误、临时路径）。
   **合并**：制度化内容 → 删除。重复项 → 保留最完整的版本。共享同一根因的 T 记录 → 合并，并加注说明被吸收的记录。
   **重编号**：合并/删除后，将剩余的 T 记录依次重编号为 T01、T02、T03……，消除空号。
   **精简**：冗长条目 → 压缩为 错误 + 深层病灶 + 下次动作 + 日期。删除"触发器"字段（它只是复述错误，没有提供额外的预防价值）。沟通偏好类跨项目规则 → 提炼到用户级 USER.md 的沟通偏好中。

   - 不要删除 30 天内的每日日志。执行删除前先向用户展示拟删除内容。

8. **当经验可流程化时，将其升格为 Skill**
   - 如果经验描述的是可复现的工作流、决策规则、触发条件，或工具/文件的修改流程，不要只把它留在记忆里。
   - 先搜索现有 skill，看是否有匹配的的职责。如果有，就更新那个 skill，而不是创建重复项。
   - 如果没有现有 skill 覆盖，就用 `skill-creator` 以及 `OPERATIONS.md` 中的治理规则创建新 skill。
   - 把这件事当作文件修改来处理：先阅读 `OPERATIONS.md` 和 `SOUL.md`，遵循 `skill-creator` 的 BP #1 关于 description 格式的要求，在顶部添加引用文件，并在 skill 较长时添加目录。
   - 让记忆成为该经验的索引；把可执行的流程细节放进 skill。

9. **验证并关闭**
   - 如果反思产出了任何实质性改动——修改原文件、计入记忆、或升为 skill——重新跑一遍触发该反思的原始场景。
   - 若修复失败，回到第 2 步（重新分析根因）或第 3 步（调整修复方案）。
   - 只有修复通过验证，才能宣布反思完成。

## 从反思中积累技能

在每次非平凡的反思之后使用这条决策规则。**去向按上文的修复手段优先级判断：能改源文件就改源文件**；源文件改不了时，按下面这张表按适用范围选（记忆或 skill），不另立一套优先级。

| 反思类型 | 持久化方式 |
|---|---|
| 关于本项目的单次事实 | 工作区每日日志或项目记忆 |
| 跨项目的行为触发器 | 教训暂存用户级 MEMORY.md；沉淀为规则时按 OPERATIONS「治理文件修改流程」第 7 步归类到对应治理文件 |
| 对现有规则或指令的纠正 | **先加载 `skill-creator`**，然后立即修改该文件 |
| 可复现的流程，或 skill/工具工作流 | **先加载 `skill-creator`**，若已有 skill 覆盖则更新现有 Skill；否则创建新 Skill |
| 影响多个 Skill 的重要模式 | 把通用规则放进治理型 Skill（加载 `skill-creator`），记忆中只保留简短索引 |
| 反复出现的错误模式（2 条及以上共享同一根因的 T 记录） | **必须升格**：找到最相关的现有 Skill 或治理文件（SOUL.md / OPERATIONS.md），先加载 `skill-creator`，再把预防规则嵌入该文件。仅靠记忆不足以应对重复模式。 |

未先加载 `skill-creator` 就修改任何 Skill 是绝对禁止的。这是一道硬性关卡。

## 质量门槛

一次反思只有在通过全部检查后才算有效：

- 它指出了被违反的具体指令，而不仅仅是"我粗心了"。
- 它区分了经过验证的事实与我的假设。
- 当模式重复时，它把当前错误与先前的案例关联起来。
- 它产出了一个下次可以执行的第一步动作。
- 如果经验应当持久化，它更新了恰当的记忆/skill。
- 它在记录经验的同时，没有再制造另一处未经授权的编辑。
- 在本次反思中修改任何 skill 之前，已加载 `skill-creator`（硬性关卡，不可协商）。
- 在制定修复方案时，已通过三条修改约束（第 3 步）。
- 在宣布反思完成之前，已输出修复方案（第 3 步）。仅有分析是不够的。
- 如果做了任何实质性改动（修改原文件 / 计入记忆 / 升为 skill），已针对原始场景验证过修复（第 9 步）。

## 常见模式

- **把推断当授权**：把"我认为 X"当作"用户确认了 X"。
- **把方案当许可**：说明了方案，然后未经明确确认就行动。
- **决策归属未经判据**：该自己判的升级给用户，或该等确认的自行代选——两个方向同根：动手前没先判"这个决策归谁"。**判据见 `OPERATIONS.md`「校准节奏」。**
- **工具替换**：用我偏好的路径替换用户指定的模型/工具。
- **绕过 skill**：未能加载一条约束着用户请求或我计划动作的 skill。
- **规则不应用于自身**：把一个规则当作文档来写，却在刚刚执行的放置/编辑中无视它。
- **只有分析没有修复方案**：完成了根因分析（第 1-2 步），却在列出具体改动之前停下。反思结束于"我找到了模式"，而非"这是要改的内容"。
